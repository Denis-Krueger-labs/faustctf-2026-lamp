\section{Root Cause and Remediation}
\label{sec:lessons}

The underlying failure was allowing externally controlled values to cross
interpreter boundaries as code. Header names became TeX control sequences;
a SQL-safe component string was later expanded as TeX; and a ship name
was written into a file that a short payload could execute through the
shell-enabled TeX process. Escaping for one destination did not protect
the next one.

The specific fixes follow directly from those boundaries:

\begin{itemize}
  \item Keep HTTP headers separate from internal request-state macros.
        Reject reserved names if dynamic macro generation remains.
  \item Accept only the three supported component types at the backend.
        Do not rely on the browser's choices or SQL escaping.
  \item Validate ship names before persistence so control characters,
        including newlines, cannot change the generated file structure.
  \item Avoid interpreting user values as TeX source. If shell escape is
        required, expose only the needed commands and run XeLaTeX with
        minimal filesystem access and an unprivileged account.
\end{itemize}

The observed impact was container-root RCE, followed by retrieval of
checker flags through the path overwrite. Disabling unrestricted shell
escape and reducing the container's privileges would limit the damage
from future TeX injection, while input separation and validation address
this chain at its entry points.
